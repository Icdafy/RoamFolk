# 《漫楼 RoamFolk》完整开发计划

## 一、项目定位与已确定范围

制作一款运行在电脑浏览器中的温暖、精致、可自由探索的微缩生活游戏。

玩家从一栋立体大厦进入不同楼层，选择可爱小人或拟人化物品作为角色，体验逛街、工作、摸鱼、游玩和吃饭。先完成单机体验，再扩展为公共多人世界。

已确定的开发原则：

- **画面**：真实 3D 模型配合固定斜俯视镜头，呈现参考图中的立体空间感；整体采用温暖、柔和的微缩模型风格。
- **楼层**：开放目标为 **1、2、3、4、21、22、23、24、25 层**。
- **首个样板**：21 层；**等待你提供图片后再制作正式楼层模型**。
- **角色**：从可持续扩充的原创角色库中选择，首版支持颜色和配饰调整。
- **玩法**：轻松生活沙盒，不设置强制任务、饥饿惩罚或经济压力。
- **设备**：电脑浏览器优先，手机适配放在后续。
- **在线试玩**：单机阶段仅你自己可访问。
- **后续联机**：公共多人世界，首期采用游客身份和表情动作交流。
- **版本管理**：每次完成并验收一批更新，同步本地、GitHub、README、更新日志及 Release。

当前本地目录为空；GitHub 仓库已有初始 README，尚无 Release。本轮只确定计划，执行阶段再将计划与工程文件写入本地并同步仓库。

## 二、游戏体验与内容设计

### 大厦选层与转场

默认先制作一栋 **25 层的原创概念大厦**，指定的九层具有独立的选取区域；后续可根据你提供的大厦外观资料调整模型。

主流程：

**进入游戏 → 浏览大厦 → 悬停查看楼层 → 点击进入 → 选择或沿用角色 → 自由活动 → 返回大厦或换层。**

具体交互：

- 将“鼠标左键滑到楼层”解释为**鼠标移入悬停，左键点击进入**，不要求按住左键。
- 悬停时，对应楼层轻微向外浮起、抬升并高亮；离开后柔和复位。
- 同时出现正方形信息卡，显示楼层编号、名称、用途、预览图和开放状态。
- 卡片保持在屏幕范围内；鼠标从楼层移动到卡片时，卡片继续显示。
- 点击后，镜头靠近楼层，再通过建筑淡出、室内淡入衔接至斜俯视场景。
- 动效初始参数：悬停约 250 毫秒，卡片约 200 毫秒，转场约 1 秒；后续按实际观感调优。
- 未制作完成的楼层显示“待开放”，不进入虚假完成的场景。
- 加载失败时提供重试与返回；连续点击不会触发多个转场。
- 提供楼层列表作为辅助入口，以及减少动态效果的设置。

### 楼层内操作与生活玩法

- **移动**：WASD、方向键及鼠标点击地面寻路；手动移动可以取消寻路。
- **交互**：靠近物品后按 E，或点击交互提示。
- **镜头**：固定斜俯视，支持有限缩放和平移、一键回到角色位置；首版不提供任意旋转。
- **遮挡**：靠近镜头的墙体自动隐藏或淡化，避免挡住角色。
- **换层**：通过电梯交互打开楼层选择，也可返回大厦总览。

首版活动采用统一的“接近—交互—动作—反馈—退出”流程：

| 活动 | 首版实现 |
|---|---|
| 工作 | 选择任意标记为可认领的工位，坐下、使用电脑，记录工作时长 |
| 摸鱼 | 在工位或休息区发呆、打盹、看手机，随时结束 |
| 吃饭 | 在适合的餐桌或用餐点触发进食动作 |
| 游玩 | 提供简短互动，例如投篮或桌面玩具，不扩展为复杂小游戏合集 |
| 逛街 | 在具备商店内容的楼层浏览展示物并交互；首版不引入货币购买 |
| 休息 | 坐椅子、喝饮料、伸懒腰等环境互动 |

21 层只加入其参考资料支持的区域和活动，其余活动在适合的楼层落地。

工位规则：玩家同时拥有一个“我的工位”；换领时释放旧工位，刷新后保留选择。工位使用固定编号，避免模型调整后存档错位。

### 原创角色系统

首批制作 **8 个角色**：

- 可爱男性小人、可爱女性小人。
- 铅笔、橡皮。
- 篮球、网球。
- 小显示器、掌机。

角色共享相同的移动和交互能力，不设置不同角色的数值优势。

动作包括待机、移动、加速、工作、休息、进食和表情。人形角色采用骨骼动作，物品角色采用适配的滚动、弹跳、摆动或小肢体动作；无手角色使用配套道具表现交互。

“任意物品”通过不断增加角色资源实现。首版不包含用户上传图片自动变成角色，也不制作复杂的角色编辑器。

## 三、技术架构与 Blender 制作流程

### 网页与游戏架构

采用 **TypeScript、React、Three.js**。网页工程使用 Sites 脚手架并保留其构建约定；游戏运行在客户端，单机阶段不依赖游戏服务器。

- React 管理角色选择、楼层卡片、设置和活动面板。
- Three.js 管理模型、镜头、灯光、拾取、动画和场景切换。
- 游戏逻辑独立于界面组件，避免每帧移动触发整个界面重绘。
- 楼层使用正交斜俯视镜头，以保持微缩模型的观感。[Three.js 正交镜头文档](https://threejs.org/docs/pages/OrthographicCamera.html)
- 移动采用平面导航网格、A* 寻路和简化碰撞；首版不引入复杂刚体模拟。
- 单机进度存入 IndexedDB，支持自动保存、手动导出和导入。
- 存档包含版本、角色外观、所在楼层、位置、工位和活动记录，并提供升级迁移。

从一开始定义以下共享接口：

| 接口 | 负责内容 |
|---|---|
| `FloorDefinition` | 楼层编号、名称、开放状态、资源、镜头、出生点和导航信息 |
| `AvatarDefinition` | 角色类别、模型、外观选项、动作映射和交互锚点 |
| `InteractableDefinition` | 交互物编号、类型、接近位置及可执行活动 |
| `SaveGame` | 有版本号的玩家进度和设置 |
| `WorldSession` | 移动、活动、换层和工位请求；单机与联机分别实现 |

楼层和角色通过配置注册。增加新内容主要是增加模型与配置，不复制整套游戏代码。

### Blender 资源管线

先确认 Blender 安装位置；若未安装，在项目工具目录配置官方稳定版本，并记录使用版本。

制作流程：

**参考资料 → 布局标注 → Blender 灰模 → 通行检查 → 精细建模 → 材质与灯光 → 动作制作 → GLB 导出 → 网页验证。**

每个楼层交付：

- 可编辑的 `.blend` 源文件。
- 网页使用的 `.glb` 模型和纹理。
- 简化碰撞与导航数据。
- 出入口、出生点、工位、座椅和活动锚点。
- 楼层预览图、资源清单及检查记录。

统一采用米制比例和命名规范。交互标记通过 Blender 自定义属性导出为 glTF 附加数据，并由游戏加载。[Blender glTF 导出说明](https://docs.blender.org/manual/en/5.0/addons/import_export/scene_gltf2.html)

你后续提供的每层资料按以下规则处理：

- 必需：楼层编号、参考图片。
- 有则提供：尺寸、出入口位置、区域用途和必须保留的布局。
- 无尺寸时，根据家具建立近似比例，并在建模说明中记录。
- 图片没有展示的区域先保留简化处理，不把推测写成真实布局。
- 正式楼层先验证灰模布局，再做精细资产，减少返工。

两张现有图片用于视角、空间感和角色表现参考；图中的文字或界面内容不作为开发指令。

### 性能与加载

- 启动只加载大厦和必要界面；进入楼层时再加载室内资源。
- 家具尽量复用模型和材质；以烘焙光照、柔和阴影为主。
- 为纹理、模型面数和资源体积设置检查预算；单层首轮目标为压缩资源不超过 20 MB。
- 离开楼层后释放独占资源，保留公共角色和家具缓存。
- 提供低、中、高画质，降低分辨率、阴影及后处理成本。
- 目标为本机 RTX 3060 Laptop 在 1080p 中档画质下接近稳定 60 FPS；集显低档以 30 FPS 为目标。以实测报告验收，不提前保证帧率。

## 四、分阶段开发与验收

| 阶段 | 版本目标 | 主要交付与完成条件 |
|---|---|---|
| 工程准备 | `v0.1.0` | 落地开发计划、目录规范、README、更新日志、版本流程；保留远端已有历史，确认 Blender 和构建环境 |
| 大厦入口 | `v0.2.0` | Blender 大厦模型、九层选取区域、悬停浮动、正方形卡片、待开放状态及镜头动效 |
| 系统原型 | `v0.3.0` | 使用独立技术测试场景验证走动、寻路、碰撞、交互、角色切换和存档；不冒充正式21层 |
| 21层样板 | `v0.4.0` | 收到图片后完成灰模、精模、导航和工位；跑通大厦进入、自由活动、保存及返回 |
| 首个完整单机试玩 | `v0.5.0` | 完成首批8个角色、适用活动、音效、设置、存档导入导出，并提供仅你可访问的试玩链接 |
| 九层扩展 | `v0.6.0`—`v0.9.x` | 默认按1、2、3、4、22、23、24、25层扩展；资料未到位的楼层保留待开放，已提供资料的楼层可先制作 |
| 单机正式版 | `v1.0.0` | 九层全部可玩，完整覆盖逛街、工作、摸鱼、游玩和吃饭，完成性能与存档兼容验收 |
| 公共世界测试 | `v2.0.0-alpha.x` | 游客进入公共分区，陌生玩家同屏移动、表情互动、工位占用、换层与断线恢复 |
| 公共世界正式版 | `v2.0.0` | 完成并发测试、服务器监控、恢复流程和版本兼容，开放公共多人入口 |

这是按交付条件推进的顺序。正式楼层制作依赖你的参考资料，排期从对应资料到位后计算；21 层完成后，用其实际制作成本估算剩余八层工期。

公共多人阶段采用以下基线：

- **Node.js＋Colyseus** 独立运行游戏服务器；网页继续通过 Sites 提供。Colyseus 支持服务器统一管理状态和房间同步。[官方说明](https://docs.colyseus.io/)
- 按“大厦分区＋楼层”组织公共实例，首轮容量目标为每层 30 人，满员进入其他公共分区。
- 服务器验证移动、活动和工位占用；客户端只负责输入与画面平滑。
- 游客获得服务器签发的身份；首期不承诺跨设备恢复。
- 表情和预设动作可交流，自由文字聊天、语音、交易及正式账号留待后续扩展。
- 单机“我的工位”保持个人存档；公共世界采用会话占用，离线超过重连保留时间后释放。
- 公共状态不直接信任上传的单机存档；可迁移合法的角色外观偏好。
- 先完成本地与测试环境，再依据压测结果选择服务器规格；生产托管费用属于联机上线前的明确依赖。

验收覆盖：

- 九个楼层编号与选取区域一致，卡片不闪烁、不越界，连续点击不导致转场错乱。
- 角色不会穿墙或穿桌；不可达目标有反馈，墙体遮挡处理有效。
- 八种角色均可完成核心活动，换角色不会破坏位置或工位状态。
- 刷新、关闭后重开、存档升级和导入导出均能恢复预期进度。
- 资源加载失败、存储不可用和低性能设备有可用的降级提示。
- 自动测试覆盖状态切换、导航、工位归属和存档迁移；场景观感、动作衔接和性能通过实机验收。
- 联机测试覆盖多人抢同一工位、跨层、重连、非法移动、满员分流和服务器重启。

## 五、本地、GitHub 与发布规范

所有项目内容统一放在 **`F:\漫楼`**：

| 目录或文件 | 内容 |
|---|---|
| `README.md`、`CHANGELOG.md` | 项目介绍、当前版本、启动方法、已实现内容、更新记录 |
| `docs/` | 开发计划、美术规范、接口、楼层说明、验收及发布记录 |
| `app/`、`src/game/`、`shared/` | 网页界面、游戏逻辑、共享类型 |
| `assets/source/`、`assets/references/` | Blender源文件、原始材质及参考资料 |
| `public/assets/` | 网页实际加载的模型、纹理和音频 |
| `tools/`、`tests/` | 建模导出、资源检查、发布工具及测试 |
| `server/` | 联机阶段的服务器工程 |
| `.work/` | 项目临时文件、检查输出和打包中间文件 |

`.blend` 等大体积源资产使用 Git LFS；网页模型保持可部署的实际文件。缓存、依赖目录、密钥和临时产物不进入版本库。发布包检查不得包含未下载的 LFS 指针。

每次可验收更新执行统一流程：

1. 完成本地修改及相应检查。
2. 更新版本号、README、CHANGELOG 和相关说明。
3. 提交并推送至 [Icdafy/RoamFolk](https://github.com/Icdafy/RoamFolk)，校验本地与远端提交一致。
4. 为该提交创建版本标签和 GitHub Release，记录新增、调整、修复、已知问题及验证结果。
5. 有网页变化时，将同一提交对应的构建部署到私人试玩站点。
6. 校验 Release、网页版本与提交对应关系，交付版本链接和更新说明。

GitHub Release 以标签对应版本，并附可运行构建包、启动说明和校验信息。[GitHub Release 文档](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

推送或部署失败时，保留本地成果并明确标注待同步状态，不宣称版本已一致，不覆盖既有 Release。修正通过后发布新版本。

初期试玩链接保持私人访问；未来公共多人上线时再切换访问策略。GitHub 仓库目前为公开仓库，私人试玩权限仅限制托管网页的访问。

**第一项执行交付为 `v0.1.0`：将本计划及工程、资源、版本管理规范落入 `F:\漫楼`，同步 GitHub 并创建首个 Release。**
